## Реалізація

| Роботи | Модуль та поведінка |
| --- | --- |
| A · контракти і права | `analytics/contracts.py` задає V1-запити та проєкції. `application/analytics.py` перевіряє сесію, роль, власника, поточні призначення викладача та зв’язки ідентичностей. |
| B · історичні джерела | `application/analytics_history.py` використовує явний SQLite-знімок, точні публікації, пакетний добір і чинні валідатори оцінки та пояснення. |
| C · агрегація | `analytics/aggregation.py` обчислює поточну аудиторію, історичну когорту, KPI, сумісні критерії, покриття та стабільний порядок. Поточна аудиторія незалежна від часу й статусу спроб. |
| D · UI | `ui/analytics_page.py`, `ui/analytics_charts.py`, `ui/shell.py` додають сторінку «Аналіз», три графіки, спільний каталог, фільтри, таблицю, фонові запити й панель деталей. |
| E · рекомендації | `analytics/recommendations.py` використовує перевірені агрегати та дозволені навчальні поради. F11-ADR-01 залишається відкритим, хмарний advisory вимкнено. |
| F · експорт | `analytics/export.py` формує версійний manifest і повну дозволену когорту. CSV використовує quoting та захист від формул. Після серіалізації виконується повторна авторизація та атомарна заміна файла. |
| G · тести | `tests/test_analytics.py`, `tests/ui/test_analytics.py` та наявні регресійні тести перевіряють SQLite, контракти, доступ, цілісність і Qt. |
| H · демонстрація | `tools/phase11_demo.py` готує нову ізольовану БД через чинний bootstrap і прикладні сервіси. |

SQLite залишається на міграції 0008. Контракти Phase 10 і learner-only API
збережено. Аналітика не викликає ScoringService й не записує історію.
Незмінний `authorization_group_id` визначає групу спроби. Суперечлива
атрибуція вилучається. Пошкоджений час завершення унеможливлює підстановку
ранішого бала в режимі останньої спроби. Помилки Mentor обліковуються окремо.
Коротка завершальна транзакція експорту резервує право запису SQLite
до перейменування локального файла, щоб зміна групи не могла набути
чинності між перевіркою та публікацією. Сесія перевіряється під тим самим
локальним блокуванням, що й відкликання токена.

## Технічні перевірки

Для sandbox-команд застосовано `UV_CACHE_DIR=/tmp/cyberforge-phase11-uv`.
`uv run --locked ruff check .` і `uv run --locked ruff format --check .`
пройшли. Ruff підтвердив формат 166 файлів. Сфокусовані перевірки
(32 пройшли) та фінальні тести WSLg Wayland (12 пройшли) виконано командами:

```bash
QT_QPA_PLATFORM=offscreen uv run --locked pytest -q tests/test_analytics.py tests/ui/test_analytics.py tests/test_learner_demo.py --tb=short
QT_QPA_PLATFORM=wayland uv run --locked pytest -q tests/ui/test_analytics.py tests/ui/test_scenarios_ui.py -k 'analytics or shared_identity or constructor_create_edit_search_and_modes' --tb=short
```

Перший sandbox-запуск Wayland не мав доступу до сокета WSLg. Тест
виконано повторно з доступом до реального сокета. Офлайн-збірка
`uv build --offline` та ізольоване встановлення wheel пройшли.
Перевірено імпорт V1 manifest зі встановленого wheel і нормальний
GUI-запуск `cyberforge --smoke-test` із новою тимчасовою SQLite.

Повний регресійний набір пройшов з **1387 тестами**, 887,60 с. Команда
`QT_QPA_PLATFORM=offscreen uv run --locked pytest -q --tb=short -o faulthandler_timeout=90 --junitxml=/tmp/cyberforge-phase11-final.xml`.
Перший sandbox-запуск зупинився в наявному тесті asyncio. Окремий офлайн
прогін `tests/test_llm_runnable.py` з доступом до локальних сокетів
пройшов усі 6 тестів. Повний набір повторено з тим самим доступом.
Фінальні результати Linux і Windows Server 2022 доступні в Checks Draft PR.


## Демонстрація та продуктивність

```bash
demo_root=$(mktemp -d /tmp/cyberforge-phase11.XXXXXX)
uv run --locked python tools/phase11_demo.py "$demo_root/fixture" --measure
QT_QPA_PLATFORM=wayland uv run --locked cyberforge --learner-demo --database "$demo_root/fixture/demo.sqlite3"
```

Bootstrap створює новий каталог і записує випадкові синтетичні паролі
лише у приватний `credentials.json`. Опція `--measure` записує два
вимірювальні експорти до цього ж демонстраційного каталогу.

Автоматично створено 2 сценарії, 3 публікації, 2 групи і 4 учні з
77 спробами. Виміряний зріз сценарію 1 охопив 53 спроби з 50
перевіреними результатами. На WSL з Python 3.12 зведення тривало 0,625 с,
із яких 0,551 с зайняла перевірка результатів та 0,002 с агрегація.
Новий знімок із пошуком та пагінацією зайняв 0,621 с, повний експорт
CSV 0,635 с і JSON 0,642 с. Це один запуск на синтетичному наборі під час локальної регресійної перевірки.
Перевірка історії коштує часу пропорційно кількості відібраних записів.
Кожна нова сторінка таблиці читає новий знімок для узгодженості KPI.
Heartbeat перевіряє актор/доступ і поточну аудиторію без читання спроб,
подій і результатів. Обсяг вибірки не обмежується розміром сторінки.

### Ручне приймання власником у WSLg

1. Відкрити `credentials.json` локально. Увійти як `teacher_demo_1`,
   відкрити «Аналіз» і вибрати «Сценарій 1». Перевірити спільний вибір з
   Конструктором. Перевірити обидві групи та поточну й історичну когорту.
2. Перемкнути «Остання завершена спроба кожного учня» й «Усі завершені
   спроби». Зіставити середній бал, знаменники й покриття; остання
   завершена спроба `learner_demo_2` очікує оцінювання.
3. Змінити версію, групу, період, стан, пошук і сортування. Перевірити
   доступність трьох графіків, рядків таблиці та кнопок на 1100×720.
4. Натиснути Enter на рядку учня. Перевірити версію, історичну групу,
   безпечну відмову з Web «Не застосовується», Web вхід та деталі
   збереженої оцінки. В історії `learner_demo_4` є пояснення Mentor.
5. Вибрати версію 1 і Групу A. Перевірити історію після відкликання дозволу
   та історичну участь `learner_demo_1` після вибуття. Архівувати
   сценарій у Конструкторі. В «Аналізі» перевірити нульову поточну
   аудиторію і збережену історію. За потреби відновити сценарій.
6. Зберегти CSV і JSON у нові файли. Зіставити дозволений зріз, manifest,
   нульові й відсутні бали. Переглянути офлайн-рекомендації та їхні межі.
7. Вийти й увійти як `Administrator_demo`. Відкрити той самий сценарій і
   перевірити доступ до всіх дозволених історичних груп адміністратора.
8. У «Адмініструванні» забрати у `teacher_demo_1` призначення до Групи B.
   У його сесії перевірити зникнення записів групи, зміну облікового запису
   та очищення сторінки при виході. Увійти як `teacher_demo_2` і
   перевірити відсутність чужого сценарію. Як учень перевірити відсутність
   навігації «Аналіз» і доступність власних результатів.
9. Відкрити другий екземпляр CyberForge з тією самою демонстраційною БД.
   У першому залишити «Аналіз» відкритим як викладач. У другому увійти
   як адміністратор і деактивувати обліковий запис викладача. Перевірити
   повернення першого екземпляра в гостьовий режим, очищення таблиці,
   деталей і порад. Відновити обліковий запис після перевірки.

Незалежний огляд і ручні кроки залишаються відкритими. Фізичний Windows 11,
DPI, GPU та інсталятор відкладено до Phase 12.
