# ADR-0003 — Ідентичність сценарію та чернеткові версії

**Статус:** технічні рішення Phase 3, очікують owner review разом із фазою.
**Джерело:** SRS v3.0 §§2.2–2.4, 3.5–3.8, 4, 11, 14, 16.6, 21, 23.
**Дата:** 12.11.2026. SRS не змінюється.

## Ідентичність і параметри

`scenarios` містить постійний SQLite AUTOINCREMENT ID, незмінного автора й
дату створення UTC. Назва завжди обчислюється як `Сценарій {id}`. Тема —
окреме поле. `scenario_versions` має унікальні `(scenario_id, number)`,
ревізію, статус, timestamps і JSON-знімок валідованих параметрів Pydantic v2.
Конструктор і read-only представлення Аналізу отримують той самий DTO через
ScenarioService, не виконують SQL і не створюють копій сценарію.

Поля відповідають §4.3: тема, бажана складність (Початкова/Середня/Висока),
необов’язкові аудиторія, опис, мета, бажані тактики, бажані NIST-ознаки листа
й додатковий JSON-об’єкт параметрів генерації. Останній зберігається лише як
дані; не запускає код, шаблони, генерацію чи зовнішні ресурси. `get()` та
`ScenarioParameters` — контракт для пізніших генераторів; артефакти мають
посилатися на конкретну версію, а не створювати інший scenario ID.

SRS не задає технічних лімітів тексту. Оборотне рішення: тема 1–2000,
аудиторія до 1000, опис/мета до 10000, тактики/ознаки до 100 записів по
1–200 символів, увесь JSON-знімок до 50000 символів. Зовнішні пробіли
обрізаються; зайві поля заборонені. Значення складності не є NIST-оцінкою.
Бажані ознаки вводяться назвами по рядках: перевіреної таксономії/підтвердження
наявності ознак ця фаза не додає. Це не заповнення майбутніх полів підтверджених
ознак або розрахунок Cue Count/Detection Difficulty.

## Статуси й конкурентні правки

Phase 3 створює тільки `draft` («Чернетка»). `published` у моделі/схемі
позначає лише майбутню незмінну межу §§4.9/11.7. Немає API/кнопки переходу
в published, ready або автоматичного призначення учням. Email/Web у новому
сценарії мають стан «Не створено»; збереження параметрів не робить їх готовими.
Публікація після всіх перевірок — Phase 8. SRS §2.3 дозволяє архівування,
але не визначає його наслідків для чернеток/публікацій. Власнику поставлено
окреме питання про включення архівування у Phase 3 або наступне вузьке завдання;
до відповіді його не реалізовано й не позначено виконаним. Нової семантики
статусів не вигадано.

Збереження змін поточної чернетки оновлює її параметри та збільшує ревізію,
залишаючи номер версії. Повторне збереження без змін нічого не змінює.
Якщо остання версія опублікована, зміни створюють наступну draft-версію,
а історичний знімок залишається незмінним. Цей шлях перевіряється тільки
fixture-даними: це не реалізація публікації. SQLite-тригери блокують UPDATE/
DELETE опублікованого знімка та зміну ідентичності/автора сценарію.

Кожен write використовує наявну транзакцію BEGIN IMMEDIATE. Збереження
вимагає очікуваних номера версії та ревізії; застарілу форму відхилено без
перезапису. Правки залишаються у формі для ручного перенесення. Немає
мовчазного overwrite, автоматичного merge правок або autosave.

## Доступ і незбережені зміни

Сервіс повторно перевіряє активну сесію та роль. Instructor читає й редагує
власні сценарії; Administrator читає всі та редагує власні. Глобальний перегляд
§2.2 не трактуємо як додаткове право редагувати чужі матеріали. Guest/Learner
не читають і не створюють чернеток; майбутні learner-publication запити
належатимуть окремому сервісу. Невідомий і чужий ID мають однакову відмову.
Автор із пов’язаними сценаріями не видаляється існуючим FK guard Phase 2.

Одна форма має guard Save/Discard/Cancel із українськими кнопками та Cancel
за замовчуванням. Він працює при зміні режиму/сторінки, Back/Forward,
виборі іншого сценарію, New, скасуванні правок і закритті вікна. Помилка Save
залишає форму й маршрут. Фільтрація та щосекундна перевірка сесії не
перезавантажують редактор. Втрата авторизації примусово очищає всі захищені
дані: revoked session не може блокувати logout або записувати правки.

## Межі

Не реалізовано LLM/MockLLMProvider, генерацію, публікацію, симуляцію,
ScoringService, аналітичні обчислення, архівування або довільні розширення
життєвого циклу. Межа архівування — відкрите owner-уточнення; затверджені
права §2.3 не скасовано. Решта реалізації не змінює затверджених вимог SRS.
