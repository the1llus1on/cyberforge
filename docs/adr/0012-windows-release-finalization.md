# ADR-0012 — Фіналізація випуску Windows та хмарні поради викладачу

**Базовий коміт:** `d45c750df5aa72817566bfacb5ca23bfb98ae126`
**Рішення D12-01–D12-10:** OWNER APPROVED (18.11.2026)
**ADR-0012 / SRS Amendment A12:** APPROVED (18.11.2026)
**Documentation Review Gate:** PASSED
**Phase 12 Architecture Freeze Gate:** PASSED
**Phase 12 implementation:** NOT STARTED / IMPLEMENTATION NOT AUTHORIZED
**WP1 Contract Freeze Gate:** PENDING IMPLEMENTATION VERIFICATION

## 1. Контекст

Phases 0–11 прийнято. [Phase 11](../PHASE_11_IMPLEMENTATION_REVIEW.md)
закрила локальну аналітику. Потрібні встановлюваний і portable-випуски,
безпечний життєвий цикл локальних даних, керована конфігурація провайдерів та
фізичне приймання Windows 11. Власник також погодив необов'язкові хмарні
рекомендації викладачу для зрізу з одним учнем. Комбінація точного бала,
версії сценарію та кількості спроб може розкрити індивідуальний результат
навіть після вилучення імені. [Поправка A12](../../TECHNICAL_SPECIFICATION.md#srs-v30--amendment-a12-windows-release-finalization)
визначає межі нового шляху.

## 2. Погоджені рішення та розглянуті варіанти

Усі десять рішень мають статус **OWNER APPROVED**. Деталізація нижче
підлягає незалежному огляду та окремому погодженню реалізації.

| ID | Рішення | Альтернатива та підстава вибору |
| --- | --- | --- |
| D12-01 | Windows 11 x64, нативний build на CPython 3.12 x64. | Збирання з WSL не дає Windows bootloader і нативних залежностей. |
| D12-02 | PyInstaller onedir і portable ZIP з повним деревом. | Onefile додає розпакування під час запуску й ускладнює перевірку Qt-ресурсів. |
| D12-03 | Inno Setup, інсталяція для поточного Windows-користувача без підвищення прав. | Загальносистемне встановлення вимагає ширших привілеїв. |
| D12-04 | Початковий адміністратор у GUI через `AccountService.bootstrap()`. | CLI-only setup незручний для готового GUI-випуску. Вбудований пароль відкривав би доступ кожному отримувачу пакета. |
| D12-05 | `QStandardPaths.AppLocalDataLocation`, приватний Windows DACL, відокремлення даних і збереження при uninstall. | Дані поруч з EXE залежать від прав і життєвого циклу каталогу програми. |
| D12-06 | Узгоджені SQLite-копії, контрольоване відновлення, оновлення й перевстановлення. | Копія відкритого головного файла може пропустити підтверджені сторінки журналу. |
| D12-07 | Обов'язкове приймання готових артефактів на фізичному Windows 11, включно з DPI, клавіатурою, GPU, WebEngine, безпекою та E2E. | Hosted CI і WSLg покривають лише частину платформної поведінки. |
| D12-08 | Manifest випуску, SHA-256, ліцензії та необов'язковий code signing. | Пакет без опису походження й хешів складніше перевірити та пов'язати з точним джерелом. |
| D12-09 | GUI для Groq/Gemini, Windows Credential Manager, Mock за замовчуванням, чинний development `.env`. | Файлова конфігурація з ключами збільшує ризик витоку через діагностику, копії та Git. |
| D12-10 | Версійна проєкція навчальних тем для хмарної поради, зокрема для одного учня. | Числові агрегати, підставні значення і поріг у п'ятьох учнів не реалізують вимогу мінімізації для одного учня. Детермінований локальний шлях залишається доступним. |

## 3. Артефакти та інсталяція

- Відтворювати build із чистого checkout зафіксованого SHA й заблокованих
  залежностей. Записати версії Windows/build, CPython x64, uv, PySide6/Qt,
  PyInstaller/hooks та Inno Setup, ідентифікатор lockfile, параметри build і
  архітектуру. Повторюваний рецепт і перевірка складу обов'язкові.
  Побайтова детермінованість артефактів потребує окремого доказу.
- Перевірити склад onedir за реальною версією Qt: `qwindows`, Qt DLL і
  залежності, `QtWebEngineProcess.exe`, Chromium resource packs, ICU,
  locales, потрібні plugins, ресурси застосунку і Alembic revisions.
  Зберегти реєстрацію внутрішньої Web-схеми до `QApplication`. Перевірити
  запуск під звичайним користувачем із шляхів з пробілами й кирилицею, без
  встановленого Python/Qt або середовища розробки. Пакет не послаблює
  sandbox, ізоляцію профілю чи контроль зовнішніх запитів.
- ZIP містить усе onedir-дерево під одним коренем. Інструкція вимагає повного
  розпакування перед запуском. Portable означає запуск без інсталяції.
  Робоча БД використовує той самий захищений AppLocalDataLocation, що й
  інстальована копія. Одночасні доступи з різних версій підлягають спільному
  блокуванню операцій обслуговування та перевірці сумісності схеми.
- Inno Setup використовує `PrivilegesRequired=lowest` без override на
  elevated mode, стабільний AppId, окремий каталог програми поточного
  користувача, ярлики та реєстрацію uninstall у його профілі. Інсталятор
  оновлює керовані файли застосунку після закриття активного процесу або
  безпечно переривається. Відсутні старі бібліотеки в активному новому
  дереві перевіряються тестом оновлення. Uninstall прибирає керовані
  файли, ярлики та власну реєстрацію, зберігає робочу БД, резервні копії,
  налаштування та записи Credential Manager. Видалення ключа доступне
  уповноваженому адміністратору в GUI.
- Manifest фіксує версію, коміт, архітектуру, інструменти, відбиток
  lockfile, артефакти, розміри, SHA-256 та стан підпису. Окремий список
  SHA-256 дозволяє перевірити фінальні ZIP та інсталятор після можливого
  підпису. Додати ліцензії та notices фактично включених компонентів і
  виконати їхні вимоги до поширення. Хеш потребує довіреного каналу
  публікації. Непідписані пакети можуть мати попередження SmartScreen або
  блокуватися політикою. Підпис також не гарантує відсутності попереджень.
  Інструкції не вимагають вимикати системний захист.
  [Qt WebEngine](https://doc.qt.io/qt-6/qtwebengine-deploying.html),
  [PyInstaller](https://pyinstaller.org/en/stable/operating-mode.html),
  [Inno Setup](https://jrsoftware.org/ishelp/topic_setup_privilegesrequired.htm),
  [Microsoft SmartScreen](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).

## 4. Перший запуск, приватне сховище та відновлення

1. Установити стабільні Qt application/organization names перед визначенням
   AppLocalDataLocation. Зберегти чинну назву `cyberforge.sqlite3` та
   виявляти існуючий стандартний шлях. Після перевірки шляху та схеми GUI
   пропонує bootstrap лише за відсутності будь-яких облікових записів у
   валідній БД. Пошкодження, заблокована БД, невдала міграція або відсутній
   доступ дають зрозумілу помилку. Скасування не створює облікового запису.
   Пароль із підтвердженням, чинна політика й Argon2id належать спільному
   сервісу. Перевірка порожньої БД та вставка серіалізовані сервісом.
   Development CLI зберігає свій контракт, installer не запускає demo seed.
2. До запису даних перевірити власника й ефективний DACL цільового каталогу,
   відхилити перенаправлення через непогоджені reparse points та небезпечні
   файлові цілі. Приватний DACL на створеному каталозі встановлюється до
   появи SQLite й успадковується БД, WAL/SHM, журналом, staging, резервними
   копіями та локальними налаштуваннями. Доступ обмежено поточним SID,
   SYSTEM і локальними Administrators. Помилка ACL припиняє запис та дає
   локальну інструкцію відновлення з дозволу власника, без автоматичної
   рекурсивної зміни наявних сторонніх каталогів. Межа захищає від інших
   звичайних Windows-користувачів. Адміністратор ОС і процеси поточного SID
   лишаються у довіреній межі.
3. Авторизований адміністратор запускає backup. SQLite Online Backup API
   створює узгоджений snapshot, включно з підтвердженим станом у WAL.
   Копію створюють у приватному staging, перевіряють відкриття, application
   schema/Alembic revision, `integrity_check`, `foreign_key_check` та SHA-256.
   Копія стає доступною після завершення перевірок. При busy, збої або
   нестачі місця робоча БД і остання валідна копія залишаються придатними.
   Backup може містити персональні результати та хеші паролів. Виведення
   копії з приватного сховища потребує явного дозволеного місця та
   еквівалентного захисту. Cloud keys до копій не входять.
4. Restore дозволено після прикладної авторизації Administrator, або в
   окремому явному локальному режимі аварійного відновлення, коли вхід
   неможливий. Такий режим спирається на контроль Windows SID над приватним
   сховищем, зупинений застосунок, перевірену копію та явне підтвердження
   заміни. Він не видає прикладну роль і після відновлення вимагає входу.
   Перевірити джерело в staging того самого тому, підтримувану схему та
   цілісність до заміни. Закрити всі з'єднання, workers і сторонні екземпляри,
   отримати виключний доступ, узгодити/прибрати sidecars без втрати
   committed state, зберегти попередній узгоджений стан. Замінити БД
   атомарною операцією на тому самому томі зі збереженням приватних прав.
   Після перевірки запуску прибрати staging. Після переривання відкрити
   підтверджений стан або зупинитися з явним відновленням. Помилковий
   restore не руйнує попередню БД. Перевірка хешу сама по собі не засвідчує
   довірене походження копії.
5. Якщо реліз змінює схему, перед `Database.upgrade()` зробити перевірену
   копію і блокувати конкурентний startup/maintenance; застосувати Alembic
   до копії, перевірити й активувати її за правилами restore. Повторний
   запуск із поточною схемою зберігає дані. Старий executable з новішою
   схемою має зупинитися до запису. Сумісний відкат вимагає узгодженої
   пари старого випуску й передоновлювальної БД та явного підтвердження,
   оскільки пізніші записи можуть бути втрачені з активної копії.
   Повторне встановлення і перехід з ZIP відкривають наявне сховище.
   [Qt QStandardPaths](https://doc.qt.io/qt-6/qstandardpaths.html),
   [Windows ACL](https://learn.microsoft.com/en-us/windows/win32/secauthz/access-control-lists),
   [SQLite Online Backup API](https://sqlite.org/backup.html).

## 5. Конфігурація провайдера і межа секретів

Прикладний Administrator із чинною сесією зберігає, замінює, вилучає
та перевіряє ключі через GUI. Налаштування діють для конкретного локального
профілю даних, керованого Administrator. Імена generic credentials мають
стабільний префікс продукту/каналу, непрозорий локальний ідентифікатор
профілю та ідентифікатор провайдера, без імен людей чи назв установ.
Той самий профіль зберігає локальний namespace при upgrade/reinstall/restore.
Restore БД не замінює vault, policy evidence чи параметри активного провайдера.
Окремі demo та production профілі мають різні namespace. Backend перевіряє
авторизацію на зміну конфігурації й використання провайдера, передає ключ
лише адаптеру, маскує введення і показує стан без повернення ключа до UI
для читання. Ключ не потрапляє до конфігурації, БД, backup, звітів,
журналів, prompt або артефактів. Провайдер одержує ключ лише в механізмі
автентифікації свого API.

Credential Manager прив'язаний до Windows-користувача. Дві CyberForge
ідентичності під одним Windows login не отримують окремих OS-vault меж
лише через namespace і RBAC. Компрометацію процесу того самого SID,
локального адміністратора чи віддаленого API ключа обробляють як
компрометацію відповідної довіреної межі.

Випуск починає з `MockLLMProvider`. Збереження ключа не активує хмару.
Адміністратор явно обирає підтримувані provider/model і активує їх.
Перевірка з'єднання є окремою явною дією із синтетичним фіксованим probe.
Невдалий доступ, вимкнення, видалення чи недоступність vault не породжують
неочікуваний виклик іншого провайдера. Збірка не використовує випадкові
`.env` із CWD чи з пакета. Чинний явний шлях конфігурації development
зберігається, а модель, доступність акаунта й privacy approval перевіряються
окремо. Активація провайдера не надає дозволу на D12-10.
[Microsoft CredWriteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritew).

## 6. Версійна межа хмарної поради D12-10

### Сумісність

`ScenarioAnalyticsService.load()` у Phase 11 авторизує роль/Scenario/
групи та виконує добір у read snapshot. Поточний `InstructorRecommendationsService`
будує локальні рекомендації з перевірених серій. `AssistantAgent` приймає
`AssistantInputV1`, який вимагає `AggregateV1` та номер версії сценарію.
`MentorFeedbackService` має свій learner-only шлях і прив'язує feedback до
перевіреної збереженої оцінки. A12 не змінює ці контракти, маршрути,
рубрики, історичні результати, RBAC, схему 0008 як baseline чи правила
змішаних версій. Підтримку нової форми окремим адаптером AssistantAgent
погоджує review, без зміни V1. F11-ADR-01 superseded лише для цього
нового topic-only шляху. Числовий Analytics cloud шлях V1 залишається
вимкненим незалежно від розміру когорти до окремого дозволу. Значення
`AggregateV1` не передаються й не підставляються.

### Вхід, локальне походження та вихід

- Запропонований контракт `assistant-topic-input-v1` — закритий об'єкт з
  двома обов'язковими полями: `schema_version` з цим літералом та
  `topics`, канонічно відсортований масив 1–4 неповторюваних значень
  `data_protection`, `link_inspection`, `reporting`, `sender_verification`.
  Сторонні поля й приведення типів заборонені. Провайдеру передається
  тільки ця проєкція разом з фіксованими інструкцією і схемою відповіді.
  Усі вихідні інструкції, формат і параметри незалежні від когорти.
- В межах нормалізованого A11 зрізу серверна межа застосунку перевіряє
  чинну сесію Instructor, належність Scenario, історичні групові права
  й застосовність критеріїв. Добір і `StoredEvaluationIntegrityValidation`
  виконуються в одному SQLite read snapshot. Джерелом є перевірені
  застосовні критерії вибраних завершених результатів зі статусом
  `SCORED`, включно зі справжнім нульовим балом. В усьому зрізі спочатку
  вибираються критерії `NOT_MET` для тем відпрацювання. Якщо застосовних
  `NOT_MET` немає, вибираються критерії `MET` для тем закріплення навичок.
  Обидві гілки використовують закриту мапу `TOPIC_BY_CRITERION`,
  видаляють дублікати й лексикографічно сортують topic IDs. Невідомі
  критерії не додають тем. Порожня проєкція дає детерміновану офлайн-пораду.
- Вибір результатів підпорядкований A11. У режимі latest-completed
  пошкоджений або `UNSCORABLE` останній результат не заміщується давнішим.
  Незастосовні критерії, `UNSCORABLE` і відсутні оцінки не породжують
  тем. Помилка цілісності вибраного джерела, операційний збій, неоднозначна
  сумісність або змішані публікації блокують cloud. За недостатніх
  перевірених джерел використовуються локальні поради. Проєкція не
  виконує повторного оцінювання та не профілює учнів.
- Відсутні learner/група/Scenario ID, версія сценарію, бали, спроби,
  лічильники або частоти, часові мітки, raw events, довільний текст,
  факти з поясненнями, ідентифікатори спроб і результатів, версії
  публікацій, ранги, приватний вміст і credentials. Стани критеріїв і
  походження теми від `MET` чи `NOT_MET` залишаються локальними. Запит
  використовує однаковий формат, інструкції та схему для обох гілок.
  Вага, порядок і повтори не кодують розмір когорти, ранжування джерел
  чи інтенсивність поведінки. Один і багато учнів з однаковими дозволеними
  темами дають однаковий payload.
- Запропонований `assistant-topic-selection-v1` повертає лише
  `schema_version` і `recommendations` з 1–4 унікальних пар
  `topic` / `recommendation_id`. Для кожної теми з вхідного набору
  допустимі лише ідентифікатори локального фіксованого каталогу,
  прив'язані до цієї теми. Наприклад, рекомендація повторити перевірку
  відправника може належати лише `sender_verification`. Не більше
  однієї пари на тему. Версію каталогу фіксує контракт; конкретний набір
  ID і тестові вектори затверджуються на Contract Freeze Gate. Невідомий
  ID, зайве поле, довільний текст або тема поза запитом відхиляє всю
  відповідь. Погоджена поведінка MVP — AI-добір і пріоритизація
  обґрунтованих, попередньо схвалених педагогічних порад. Модель вибирає
  ID і порядок, а UI відображає українські тексти з локального каталогу.
  Тексти придатні для обох гілок і не стверджують фактичний стан критерію.
  Модель не створює балів, тверджень про результати, довільних персональних
  оцінок чи дій від імені викладача. Вільна генерація тексту потребує
  окремого майбутнього архітектурного рішення.

### Згода, контроль над відправленням і скасування

1. Організація окремо дозволяє мету, локальний обсяг реальних даних і
   конкретний акаунт/проєкт, провайдер, endpoint і режим, перевіряє
   застосовну правову підставу, умови обробки, використання для навчання
   моделей, retention/monitoring, доступ людини та передачу за межі
   юрисдикції. Доказ рішення має відповідального, строк і механізм
   відкликання. Стан дозволу й privacy profile локальні та змінюються
   лише через уповноважену організацією процедуру. Запис звіряється з
   фактичним акаунтом і endpoint, а після заміни ключа чи параметрів
   потребує повторної перевірки. Дозвіл не успадковується від іншого
   профілю або з відновленої БД. Instructor RBAC,
   окремий клік, наявність ключа та опубліковані умови самі по собі не є
   доказом дозволу. Невідомий, прострочений, непідтверджений або
   відкликаний статус, невідповідність конфігурації чи ризик визначення
   особи згідно з політикою блокують cloud. Статус перевіряють і для
   синтетичного режиму за його окремою політикою; походження реальних
   результатів не маркують як synthetic.
2. Після закриття snapshot UI показує точний вихідний payload, фіксовані
   інструкції/схему, одержувача, мету та попередження про залишкову
   можливість зв'язування. Instructor явно підтверджує кожний виклик.
   Одноразове підтвердження локально зв'язане із сесією, поколінням
   UI-запиту, нормалізованим зрізом, перевіреним набором джерел, provider
   profile і канонічним payload. Перед відправленням повторно перевірити
   ці прив'язки, актуальність дозволу та проєкцію у свіжому read snapshot;
   зміна вимагає нового preview. Інвалідацію та допуск до dispatch
   серіалізувати на локальній прикладній межі. Worker повторно звіряє
   стан безпосередньо перед provider dispatch. Ідентифікатори та відбитки прив'язки
   лишаються локальними.
3. Відправлення через `LLMGateway` після завершення транзакції. Для
   D12-10 обмежити Gateway одним підтвердженим зверненням, без
   автоматичного повтору, repair prompt або failover. Інший endpoint
   потребує нового preview і підтвердження. У provider boundary перед
   мережею перевірити зібраний запит: лише фіксовані інструкції та
   дозволені поля контракту, без історії, інструментів, telemetry IDs і
   персоналізованих метаданих. Provider/model/API auth і звичайні
   транспортні метадані неминучі. Статуси помилок нормалізувати, tracing
   payload вимкнути включно з SDK, diagnostics і crash reports. Допустимі
   локальні журнали містять лише категорію події та узагальнений статус,
   без тем, payload, відповіді, токенів сесії чи зв'язку з учнем.
4. Logout, revoke, зміна Scenario/фільтрів або privacy/provider profile
   анулюють preview та локальний результат. Відмова, недоступність,
   таймаут або невалідний вихід дають детерміновані офлайн-рекомендації
   лише в поточному авторизованому зрізі. Для відкликаної сесії очистити
   і локальні поради. Скасувати незапущені завдання, припинити активне
   завдання за можливості та завжди відкинути застарілу відповідь після
   повторної авторизації, звірки зрізу, покоління й дозволу. Скасування
   не відкликає вже передані дані. Зміни результатів, оцінювання,
   feedback, публікацій і навчальних призначень заборонені.

Теми мінімізують обсяг розкриття. Навіть тема в поєднанні з мережевим
часом, акаунтом провайдера, зовнішніми знаннями або повторними запитами може
дозволити зробити висновок про людину. Тому немає гарантії анонімності.
Review перевіряє послідовні вузькі зрізи, помилки телеметрії, race між
перевіркою доступу й мережею, відмінності реальних provider adapters і
умови конкретного акаунта. Стан або версія договору поза строком дії
означає локальний режим. Публічні джерела описують умови продукту.
Підтвердження конфігурації конкретного акаунта є окремим доказом.
[NIST SP 800-188](https://csrc.nist.gov/pubs/sp/800/188/final),
[OWASP LLM02](https://genai.owasp.org/llmrisk/llm022025-sensitive-information-disclosure/),
[Groq Data Controls](https://console.groq.com/docs/your-data),
[Gemini API Terms](https://ai.google.dev/gemini-api/terms).

### 8.1. Вектори проєкції D12-10

Це специфікація майбутніх перевірок P12-10 і P12-11. Для позитивних
векторів чинні всі перевірки авторизації, організаційної політики й
налаштувань провайдера. Після перегляду точного preview та явного
підтвердження Instructor дозволено один виклик через `LLMGateway`.
Очікуваний payload у позитивних випадках містить тільки
`schema_version: "assistant-topic-input-v1"` і `topics`. Теми в обох
гілках мають спільну мапу та канонічний порядок.

| Вхідний зріз | Очікуваний результат |
| --- | --- |
| Один учень, перевірений `SCORED` з застосовним `NOT_MET`, що має тему. | Дозволений запит. `topics` дорівнює відсортованій множині тем від усіх застосовних `NOT_MET`. Теми, наявні тільки в `MET`, не додаються. |
| Один учень, перевірений `SCORED`, усі застосовні критерії `MET` і хоча б один має тему. | Дозволений запит. `topics` дорівнює відсортованій множині тем застосовних `MET`. За однакового набору тем з першим вектором канонічні payload та інструкції однакові. |
| Один учень, перевірений `SCORED` зі справжнім балом 0 і застосовним `NOT_MET` з мапи. | Дозволений запит із темами `NOT_MET`. Нуль не передається і не перетворюється на відсутній результат. |
| Один учень без завершеної оціненої спроби, включно з завершеною спробою без оцінки. | Без виклику. Детермінована локальна порада для авторизованого зрізу без висновку про успішність. |
| Один учень, останній вибраний результат `UNSCORABLE`, є давніший `SCORED`. | У latest-completed без виклику. Давніший результат не заміщує вибраний, застосовується локальна порада. |
| Один учень, останній вибраний результат має помилку цілісності, є давніший `SCORED`. | У latest-completed без виклику та підстановки давнішого. Локальна порада тільки в дозволеному зрізі. |
| Кілька учнів в одній публікації, повторювані теми дають ту саму дозволену множину, що й одноосібний зріз. | Канонічний payload і фіксовані інструкції збігаються з одноосібним зрізом. Розмір когорти та повтори не передаються. |
| Instructor без доступу або з відкликаною сесією. | Без виклику, preview або видачі порад для недоступного зрізу. |
| Зріз зі змішаних публікацій, кожна з яких окремо має перевірені теми. | Без виклику, детермінована локальна порада для чинного авторизованого зрізу. |

## 9. Демонстраційні дані

Релізна інструкція має описати версійний seed з чинними synthetic fixtures
для ролей, груп, публікацій, двох завершених шляхів, відновлення спроби й
аналітики. В окремому тестовому профілі використовуються відтворюваний
порядок дій та очікувані оцінки, а паролі генеруються випадково та
зберігаються приватно. Повторний setup або відхиляється для зайнятого
шляху, або зберігає вже ініціалізовані дані. Перевірки включають
локальний режим за замовчуванням та контрольований D12-10 probe на mock
transport. Будь-яка окрема live перевірка потребує дозволеної конфігурації.
